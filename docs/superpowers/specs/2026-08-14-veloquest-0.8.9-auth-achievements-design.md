## 1. Goal

Deliver VeloQuest 0.8.9 with production-ready Google authentication, a secure VK ID OAuth bridge, account architecture compatible with future Sign in with Apple, and a server-authoritative achievement/reward engine. Preserve email/password, recovery, persisted sessions, account isolation, canonical Ride, XP ledger, H3, quests, privacy masking, Garage trust boundaries, and all 0.8.8 behavior.

Physical-device OAuth E2E remains an explicit release gate. No provider integration may be declared operational until a real provider application, credentials, redirect configuration, and device flow have been verified.

## 2. Non-goals

- No visible or non-functional Apple button.
- No Apple Developer Program purchase.
- No leaderboard or rewards for absolute/max speed.
- No client-side achievement, progress, XP, or reward writes.
- No reward for manual or historical GPX/FIT, duplicate imports, GPS spikes, or untrusted client metrics.
- No virtual reward represented as a real bicycle component.
- No achievement administration UI in 0.8.9.
- No production mutation before the complete preflight is green.
- No retroactive reward backfill is required because the production user tables are empty at this checkpoint.

## 3. Authentication architecture

### 3.1 Shared client behavior

The Supabase client uses PKCE, AsyncStorage session persistence, auto-refresh, process locking, and application lifecycle refresh handling. The canonical application callback is:

- veloquest://auth/callback

The callback parser accepts only allowlisted schemes, hosts, parameters, and providers. It distinguishes cancellation, provider error, missing/expired code, replay, and successful completion. Every asynchronous completion is guarded by the existing account epoch so a callback started for account A cannot mutate account B.

Email/password registration, login, recovery through veloquest://reset-password, logout, persisted session, delete-account, and account isolation remain supported.

### 3.2 Google

Google uses Supabase Auth directly:

1. Client calls signInWithOAuth for provider google with skipBrowserRedirect and redirectTo veloquest://auth/callback.
2. Expo WebBrowser opens the returned authorization URL.
3. The callback returns an authorization code.
4. The client exchanges the code once through exchangeCodeForSession.
5. Supabase persists and refreshes the resulting session.
6. Cancellation or malformed callback leaves the current session unchanged.

Provider-console callback:

- https://rvqiptyzsjcunzjhofid.supabase.co/auth/v1/callback

Supabase Auth URL allowlist entry:

- veloquest://auth/callback

Automatic linking is delegated only to Supabase verified-identity behavior. The application does not implement email-only fallback linking. Manual Google linking is available only from an authenticated account using linkIdentity and requires explicit user action.

### 3.3 VK ID OAuth bridge

VK ID is not treated as a native Supabase provider. The bridge consists of:

- vk-auth-start: creates a short-lived authorization transaction.
- vk-auth-callback: validates and exchanges the VK authorization response.
- vk-auth-finish: atomically consumes the application ticket and completes sign-in.
- private.oauth_transactions: server-only state, PKCE, nonce, intent, expiry, and consumption data.
- private.external_identities: stable provider-subject to Supabase user binding.

VK trusted redirect URI:

- https://rvqiptyzsjcunzjhofid.supabase.co/functions/v1/vk-auth-callback

Flow:

1. The client asks vk-auth-start for a sign-in or link flow.
2. The function creates cryptographically random state, PKCE verifier/challenge, nonce, and a five-minute expiry. Link intent also records the authenticated Supabase user.
3. The client opens the returned VK ID OAuth 2.1 authorization URL in the system browser.
4. VK redirects only to vk-auth-callback.
5. The callback validates state, expiry, unused status, exact redirect URI, callback shape, and provider errors before exchanging the code.
6. VK application credentials and any secure key remain only in Supabase Secrets. Token exchange and profile lookup occur only on the backend.
7. The bridge validates issuer, audience, nonce, expiry, and the stable VK subject when an ID token is supplied.
8. For sign-in, the bridge resolves the existing provider-subject binding or creates an isolated Supabase account with an internal non-deliverable identity. VK email is profile data only and never causes automatic account merging.
9. The callback redirects to veloquest://auth/callback with a random one-time bridge ticket, never a VK access token, refresh token, application secret, service-role key, or Supabase session.
10. vk-auth-finish atomically consumes the ticket and returns only the one-time Supabase verification material needed by the client to establish its persisted session.
11. Replay, expired ticket, already-linked subject, or ownership conflict fails closed.

A signed-in user may explicitly connect VK. Link mode proves control of both the current Supabase session and the VK identity. It never merges users solely because VK reports an email matching another account.

### 3.4 Future Apple compatibility

The external identity contract supports provider apple and a unique provider subject without schema replacement. Apple display name fields are optional because Apple may return them only on first authorization. Native Sign in with Apple will be added only after the required Apple capability and paid developer setup are available. Until then, Apple is absent from the UI.

## 4. Achievement and reward architecture

### 4.1 Product model

Approved model:

- badges;
- titles;
- profile decoration;
- cosmetic VeloQuest Bike items;
- collection progress;
- small one-time XP bonuses.

Cosmetics do not change ride performance, compatibility, real bicycle configuration, or reward multipliers. Achievement XP uses the existing server-authoritative XP ledger and is intentionally secondary to ride/quest progression.

### 4.2 Data model

achievement_definitions

- Stable code plus integer version.
- Status: draft, active, retired.
- Category, title, description, evaluator key, criteria snapshot, reward XP, cosmetic reward codes, effective dates.
- Only one active version per achievement code.
- Definition updates never delete or revoke an existing unlock.

achievement_progress

- Owned by user, definition code/version, current and target values, last eligible server event, and updated timestamp.
- Clients may read only their own progress.
- All writes are performed by security-definer server functions with a fixed search path and revoked public execution where appropriate.

achievement_unlocks

- Immutable one-row unlock per user and stable achievement code.
- Records definition version, source event, optional canonical ride, evidence snapshot, unlock time, and unique reward key.
- No update/delete path for clients.
- A later definition version does not remove or re-award an existing unlock.

cosmetic_rewards and user_cosmetic_rewards

- Public read-only reward catalog.
- User ownership rows are immutable grants with a globally unique reward key.
- Virtual rewards are explicitly marked cosmetic and cannot reference real component fitments.

achievement_events

- Server-created verified events.
- Canonical unique event key prevents duplicate processing.
- Ride events reference the canonical ride and its reward eligibility snapshot.

### 4.3 Evaluation boundary

The ride processor emits an achievement event only after canonical ride persistence, duplicate resolution, historical/manual classification, privacy-safe metric calculation, and the existing XP transaction.

The achievement evaluator runs in the database transaction under a per-user lock. Unique constraints provide the final idempotency boundary:

- one event per canonical source event;
- one unlock per user and achievement code;
- one XP ledger entry per achievement reward key;
- one cosmetic grant per reward key.

Concurrent invocation may observe a conflict but cannot mint duplicate progress, XP, unlocks, or cosmetics.

### 4.4 Reward eligibility

A ride can affect achievements only when all of the following are server-established:

- canonical and owned by the user;
- not cross-source duplicate;
- not manual/historical GPX or FIT;
- eligible under the existing ride reward policy;
- timestamps and route metrics are trustworthy;
- no impossible segment speed or GPS teleport;
- metric-specific sample coverage passes its server threshold.

The client cannot send achievement codes, progress deltas, unlocked flags, XP amounts, reward keys, baselines, or eligibility overrides.

### 4.5 Safe achievement categories

Initial categories:

- first verified ride;
- cumulative verified distance;
- cumulative verified elevation;
- regularity and ride streaks;
- new H3 territory;
- completed quests;
- Regional Adventure;
- new districts and route types;
- cadence consistency;
- sustainable tempo consistency;
- improvement relative to a personal server-owned baseline.

Cadence consistency uses a bounded physiological range, minimum valid sample count, minimum moving-time coverage, duration, and variability threshold. It rewards stable pedaling, not highest cadence.

Tempo consistency ignores max speed and GPS peaks. It uses validated moving segments and rewards low variability over a safe sustained interval.

Personal improvement compares server-generated baselines and comparable verified rides. It cannot be claimed from a client-supplied baseline or a single anomalous ride.

### 4.6 Initial reward policy

- Small XP grants are one-time and encoded in the immutable definition version.
- No repeatable achievement XP in 0.8.9.
- No achievement grants more XP than a normal verified ride reward.
- Cosmetic rewards have no gameplay power.
- Retiring or tightening a definition preserves prior grants.
- Relaxing a definition evaluates only users without an existing unlock.
- No reward is created merely because a definition changes version.

## 5. Client surfaces

AuthScreen adds visible Google and VK actions with provider-specific loading, cancellation, and error states. Apple is not rendered.

Profile adds:

- linked identity list;
- explicit connect Google/VK actions;
- unlink protection that prevents removing the last usable sign-in method;
- achievements summary;
- badge/title/cosmetic collection;
- progress display sourced only from server views.

The client may optimistically display browser progress only. It may not optimistically display an unlock, XP increase, or cosmetic ownership before the server response.

## 6. Security and RLS

- private OAuth and identity tables are inaccessible to anon/authenticated clients.
- Service-role secrets exist only in Edge runtime secrets.
- Public achievement definitions/reward catalog are read-only.
- Users can read only their own progress, unlocks, and cosmetic grants.
- No client insert/update/delete policy exists for progression tables or XP ledger.
- Security-definer functions pin search_path, validate auth.uid, and revoke unintended execute privileges.
- Delete-account removes provider bindings, pending OAuth transactions, achievement progress/unlocks, and cosmetics through controlled ownership cleanup while preserving no orphaned login path.
- Logs redact authorization codes, tokens, ticket values, PKCE verifier, secrets, exact private route data, and user email.

## 7. Failure handling

- Browser cancellation: return to auth screen with no session mutation.
- Provider denial/error: normalized safe error, diagnostic code, no secret material.
- Callback without code/state: fail closed.
- Expired/replayed state or ticket: fail closed and require a new flow.
- Provider identity already bound elsewhere: explicit conflict; no merge.
- Network failure after provider approval: user may safely retry; completed one-time objects cannot be replayed.
- Achievement evaluator failure: canonical ride remains recorded, event remains retryable, and no partial XP/cosmetic grant commits.
- Duplicate/concurrent event: returns existing server state without a second reward.

## 8. Verification gates

### 8.1 Tests-first cycle

Every behavior starts with a failing test, then minimal implementation, green run, and refactor. Required automated coverage:

- Google callback parsing, cancellation, malformed response, and one-time code exchange.
- VK state, PKCE, nonce, expiry, replay, callback shape, ticket consumption, identity conflict, sign-in, and explicit linking.
- Account A to B async callback isolation.
- Apple provider compatibility without Apple UI.
- Definition versioning, progress, immutable unlock, cosmetic grant, and XP reward.
- Duplicate canonical ride protection.
- manual/historical GPX/FIT protection.
- forged client XP/progress rejection.
- GPS spike rejection.
- cadence/tempo sample-quality rejection.
- idempotent retry and concurrent processing.
- preservation of old unlocks after definition change.

### 8.2 Database and build gates

Before production mutation:

1. Exact migration generation check.
2. Clean local Supabase reset twice.
3. Database tests.
4. Two-user RLS smoke.
5. Forged XP/progress smoke.
6. Duplicate, historical/manual, idempotency, and concurrency smoke.

### 8.3 Provider and physical-device gates

Google and VK require real provider applications and credentials before live E2E. Required physical scenarios:

- iPhone;
- iPad portrait;
- Android phone;
- Android tablet portrait;
- sign-in, cancellation, denial, malformed callback, persisted session, re-login, linking conflict, account isolation, disconnect, and delete account;
- achievements, reward idempotency, duplicate/historical rejection, GPS spike rejection, Light/Dark, and screenshots.

No physical E2E claim is allowed until these scenarios run on actual devices.

## 9. Production rollout

Production remains unchanged until all credential-independent gates are green. The production delta contains only reviewed migrations, Edge Functions, provider configuration, and versioned client changes. Apply in controlled order, run transactional smoke, authenticated provider smoke, observation, cleanup, and verify P0 equals zero. Any provider requiring user console access or credentials pauses exactly at that external gate.
